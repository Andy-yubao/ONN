我认为**很有必要用 GitHub 同步**。这个课题并不只是“存放代码”，后续会同时涉及：

* 神经网络训练与部署
* FPGA 工程
* PCB 与外围电路
* 器件选型和接口定义
* 实验记录
* 多人协作与任务分工

如果只通过微信传文件或各自在本地保存，很容易出现“哪个才是最新版”“这个接口是谁改的”“为什么当时选这个器件”之类的问题。GitHub 最大的价值不是云盘，而是**版本管理、变更记录和协作过程可追溯**。

## 一、PCB 和 FPGA 文件是否适合放 GitHub

### 1. PCB 工程通常可以直接上传

PCB 项目本身一般没有想象中那么大。原理图、PCB 布局、封装库通常是若干文本或工程文件，常见规模一般可以接受。

建议上传：

* 原理图工程
* PCB Layout 工程
* 自建封装和符号库
* BOM
* Gerber
* 钻孔文件
* 坐标文件
* 原理图 PDF
* 关键设计说明

不建议上传：

* 软件自动生成的缓存
* 本地用户配置
* 临时文件
* 自动备份目录
* 大量历史导出文件
* 软件安装包

即使某些 PCB 工程文件是二进制格式，Git 仍然可以保存，只是无法像代码一样逐行比较。对于课题规模来说，这并不是严重问题。

### 2. FPGA 工程需要有选择地上传

FPGA 工程里真正重要的源文件通常并不大，例如：

* Verilog/SystemVerilog 源码
* 约束文件
* IP 配置文件
* 仿真 testbench
* TCL 脚本
* 工程配置
* README

真正占空间的是 Vivado、Quartus 或 Questa 自动生成的内容，例如：

* 综合结果
* 实现结果
* 仿真缓存
* 编译数据库
* 日志
* bitstream 中间产物
* IP 自动生成文件
* 各种临时目录

这些通常**没有必要全部上传**。只要源文件和工程重建所需配置齐全，其他成员就可以重新生成。

因此核心原则是：

> 上传“人编写的源文件”和“重建工程所必需的文件”，忽略“软件可以重新生成的文件”。

### 3. 神经网络模型文件要区别处理

训练代码、配置文件和小型测试数据可以直接放 GitHub。

但这些内容不建议直接长期提交：

* 大型数据集
* 每个 epoch 的 checkpoint
* 大型 `.pth`、`.pt`、`.onnx`
* 大量日志和 TensorBoard 文件
* 中间特征和缓存

最终需要发布的少量模型，可以：

* 使用 Git LFS；
* 放在 GitHub Release；
* 或存入网盘，在文档中记录下载地址和校验值。

现阶段你们甚至可以先不使用 Git LFS。等真的出现几十 MB 以上、且必须版本管理的模型文件，再引入也不迟。

# 二、推荐的仓库组织方式

现在项目还处于需求和方案阶段，建议先建一个统一仓库，而不是立刻拆成多个仓库。

```text
onn-project/
│
├─ README.md
├─ LICENSE
├─ .gitignore
│
├─ docs/
│  ├─ 01_project_overview.md
│  ├─ 02_requirements.md
│  ├─ 03_system_architecture.md
│  ├─ 04_interface_specification.md
│  ├─ 05_development_plan.md
│  ├─ 06_risk_register.md
│  ├─ 07_meeting_notes.md
│  └─ decisions/
│
├─ hardware/
│  ├─ pcb/
│  ├─ components/
│  ├─ datasheets/
│  └─ mechanical/
│
├─ fpga/
│  ├─ rtl/
│  ├─ tb/
│  ├─ constraints/
│  ├─ scripts/
│  ├─ ip/
│  └─ README.md
│
├─ model/
│  ├─ training/
│  ├─ deployment/
│  ├─ configs/
│  ├─ evaluation/
│  └─ README.md
│
├─ experiments/
│  ├─ templates/
│  └─ records/
│
├─ tools/
│
└─ outputs/
```

这里的 `outputs/` 可以只保存少量最终结果，或者整体加入 `.gitignore`。

# 三、现阶段最应该创建的文档

不建议一开始写十几份很正式的长文档。你们当前最需要的是几份能够持续更新的“活文档”。

## 1. `README.md`

这是进入仓库后首先看到的内容，建议包括：

* 项目名称
* 一句话目标
* 当前阶段
* 系统整体组成
* 仓库目录说明
* 当前成员及分工
* 如何开始阅读项目
* 最近的主要任务

例如项目目标可以暂时写成：

> 本项目研究面向低功耗、高速推理的光电混合神经网络系统，探索光学前端、模拟信号采集、神经网络模型与 FPGA 部署之间的协同设计。

这里的表述以后可以随着你们对课题理解加深而修改。

## 2. `docs/01_project_overview.md`：课题总览

它回答“我们到底在做什么”。

建议包含：

* 研究背景
* 最终系统希望实现什么
* 输入是什么
* 输出是什么
* 光学器件承担什么功能
* FPGA 承担什么功能
* 神经网络承担什么功能
* 当前仍未确定的问题
* 第一阶段原型的最小目标

尤其要明确区分：

* 最终理想系统
* 暑假阶段可以完成的系统
* 当前最近两周要验证的系统

否则项目很容易从一开始就失控。

## 3. `docs/02_requirements.md`：需求文档

需求不要只写“实现神经网络部署”，而应尽量写成可验证形式。

可以按层次划分：

### 功能需求

* 能够采集光电器件输出
* 能够完成 ADC 数据读取
* 能够将数据送入 FPGA
* 能够执行指定神经网络推理
* 能够输出分类或回归结果

### 性能需求

目前不能确定的数字可以标记为 `TBD`：

| 指标      |  目标 | 当前状态 |
| ------- | --: | ---- |
| 输入通道数   | TBD | 未确定  |
| ADC 采样率 | TBD | 未确定  |
| ADC 位宽  | TBD | 未确定  |
| 推理延迟    | TBD | 未确定  |
| FPGA 功耗 | TBD | 未确定  |
| 模型准确率   | TBD | 未确定  |

这不是形式主义。它能够直接暴露出你们还需要向老师或研究生询问哪些问题。

## 4. `docs/03_system_architecture.md`：系统架构

建议画出一条完整的数据链：

```text
光学输入
  ↓
光学器件 / 光电探测器
  ↓
模拟前端：放大、滤波、偏置
  ↓
ADC
  ↓
FPGA 数据接收
  ↓
预处理
  ↓
神经网络推理
  ↓
结果输出
```

每个模块下面记录：

* 输入
* 输出
* 数据类型
* 预计带宽
* 负责人
* 当前状态
* 依赖条件

这份文档会成为 PCB、FPGA 和模型三部分之间的“总接口”。

## 5. `docs/04_interface_specification.md`：接口定义

我认为这份文档非常关键，因为你已经意识到两个部分之间耦合很强。

需要逐步记录：

* 光电器件输出是电压还是电流
* 输出范围
* 通道数量
* 模拟带宽
* ADC 型号及接口
* ADC 位宽和采样率
* FPGA 接收方式
* 时钟频率
* 数据排列格式
* 定点数格式
* 模型输入张量形状
* FPGA 输出结果格式

例如：

```text
ADC → FPGA 数据接口

状态：待确认
通道数：TBD
每通道位宽：TBD
采样率：TBD
电平标准：TBD
时钟来源：TBD
数据有效信号：TBD
```

刚开始大部分是 `TBD` 完全没有问题。文档的意义之一就是集中保存未知项。

## 6. `docs/05_development_plan.md`：开发计划

建议不要只按“PCB、FPGA、模型”三条线分别制定计划，而要按**可验证的里程碑**组织。

例如：

### M0：课题定义明确

* 明确光学器件的职责
* 明确输入输出
* 明确现有器件和开发板
* 明确暑假阶段目标

### M1：纯软件基线

* 确定任务和数据
* 训练最小模型
* 确定模型输入输出
* 获得准确率、计算量和参数量

### M2：FPGA 数字链路验证

* 用模拟数据替代 ADC
* FPGA 接收输入
* 完成基础运算或简化模型
* 验证输出正确

### M3：模拟采集链路验证

* 光电器件产生信号
* 模拟前端输出稳定
* ADC 正确采样
* FPGA 能读取真实数据

### M4：系统联调

* 真实光学输入
* 完整采集
* FPGA 推理
* 结果输出
* 测量延迟、功耗和准确率

这种计划比“第一周学 Verilog，第二周画 PCB”更可靠，因为每个阶段都有明确可见的结果。

## 7. `hardware/components/component_list.md`：器件清单

建议至少记录：

| 器件   | 型号             | 用途    | 关键参数         |  数量 | 状态    | 资料 |
| ---- | -------------- | ----- | ------------ | --: | ----- | -- |
| FPGA | Cyclone IV 某型号 | 推理与控制 | 逻辑资源、RAM、DSP |   1 | 已有/待定 | 链接 |
| ADC  | TBD            | 模数转换  | 位宽、采样率、接口    |   1 | 待选    |    |
| 光电器件 | TBD            | 光电转换  | 响应度、带宽       | TBD | 待确认   |    |

不要只保存 datasheet，还要写清楚：

> 为什么选它，它在系统中做什么，哪些参数决定它能否使用。

否则几个月后即使还留着 PDF，也很难回忆当时的选型逻辑。

## 8. `docs/decisions/`：设计决策记录

每当遇到一个重要选择，可以增加一个很短的文档，例如：

```text
docs/decisions/
├─ 001-use-fixed-point.md
├─ 002-select-adc-interface.md
└─ 003-model-deployment-format.md
```

内容只需包括：

* 问题是什么
* 考虑过哪些方案
* 最终选择
* 选择原因
* 可能的后果

例如：

```markdown
# 是否采用定点数推理

## 决策
第一版 FPGA 原型采用 INT8 或自定义定点数，而不是浮点数。

## 原因
- 降低 DSP 和逻辑资源消耗
- 减少存储与带宽需求
- 更符合低功耗目标

## 待验证
量化后准确率是否可以接受。
```

这是科研项目中非常有价值、但最容易被忽略的内容。

## 9. `experiments/records/`：实验记录

每次实验创建一份文件：

```text
2026-07-19_adc-loopback-test.md
2026-07-23_fpga-matrix-multiply.md
```

建议模板：

```markdown
# 实验名称

## 目的

## 日期和参与者

## 使用硬件与软件版本

## 实验步骤

## 参数配置

## 结果

## 异常现象

## 结论

## 下一步
```

要重点记录“失败实验”。成功结果往往可以重新得到，但失败的原因很容易被遗忘和重复踩坑。

## 10. `docs/meeting_notes.md` 或单独会议记录

每次组会记录：

* 老师提出了什么
* 有哪些新定义
* 做了哪些决定
* 谁负责什么
* 下次组会前需要完成什么
* 哪些问题需要向研究生询问

不必记录所有对话，只记录**决策和行动项**。

# 四、现阶段不必急着创建的内容

暂时不用投入太多时间做：

* 很正式的软件需求规格书
* 复杂的贡献规范
* 自动化发布流程
* 大量 GitHub Actions
* 完整 API 文档
* 很细的编码规范
* 多仓库拆分
* 过度复杂的项目管理系统

你们当前最重要的是让“课题定义—系统架构—接口—实验”形成闭环。

# 五、GitHub 上配合使用的功能

除了存文件，我建议使用：

### Issues

每个相对独立的任务建一个 Issue，例如：

* 确认光学器件输出信号类型
* 调研 ADC 选型
* 搭建 FPGA 仿真环境
* 建立软件模型基线
* 测试 Cyclone IV DSP 资源

Issue 中可以记录结论，不必所有事情都塞进一个开发计划文档。

### Projects 看板

只需要最简单的四列：

```text
Backlog → Todo → In Progress → Done
```

暂时不要建立很复杂的敏捷管理流程。

### Pull Request

即使团队人数不多，也建议重要改动通过分支和 PR 合并，尤其是：

* 修改接口定义
* 修改系统架构
* 修改 FPGA 顶层接口
* 修改 PCB
* 修改模型输入输出格式

这样其他人至少能看到“什么发生了变化”。

# 六、我建议你们现在立刻建立的最小版本

第一天不需要把上面全部写完。先创建这些：

```text
README.md
docs/
├─ project_overview.md
├─ requirements.md
├─ system_architecture.md
├─ interface_specification.md
├─ development_plan.md
├─ open_questions.md
└─ meeting_notes/
hardware/
├─ components/
└─ datasheets/
fpga/
model/
experiments/
.gitignore
```

其中 `open_questions.md` 很适合你们当前阶段，可以先把不知道的问题全部放进去：

```markdown
# 待确认问题

## 光学部分
- 光学器件是否只承担信号采集？
- 是否包含光学卷积、矩阵乘法或其他计算？
- 输出信号形式是什么？
- 输出通道数和带宽是多少？

## 电路部分
- 是否已有指定的光电探测器和 ADC？
- 模拟前端是否已有参考设计？
- 信号动态范围是多少？

## FPGA 部分
- 最终使用哪块 FPGA？
- 模型是否必须完全运行在 FPGA 上？
- 是否允许使用外部存储器？
- 延迟和功耗目标是多少？

## 模型部分
- 具体任务是什么？
- 使用什么数据集？
- 光学前端输出如何映射为网络输入？
- 准确率要求是多少？
```

从你们现在的状态来看，这份“待确认问题”甚至比写完整需求文档更重要。

总体而言，我的建议是：**所有能够体现项目知识和决策的内容都放 GitHub；可以自动重新生成的大文件不放；模型、数据和构建产物按需使用 Git LFS、Release 或外部存储。**这样 GitHub 最终会成为项目的“唯一可信信息源”，而不是单纯的代码仓库。
